## Context

`ARCHITECTURE.md` §1–§6 and ADR 0003 already say: the engine is an HTTP service, n8n holds the
triggers/sequences/waits, prompts and rules are rows, humans confirm. None of the HTTP surface or
n8n exists (`packages/engine` has no `api/`; there is no `n8n/workflows/`; n8n is not installed).
Every step has been run by hand from the CLI — which is how each paper got imported twice
(`legacy.import_scan` inserts a fresh `capture` unconditionally; 6 child×paper pairs have two
reads each, 43 "confirmed" answers on a 24-question paper). The read prompts are configured on
`claude-sonnet-5` in the `prompt` table — that is where the $10 went. `gold` exists and is empty;
`read_confidence` and `read.auto_confirm_above` are never written or read; there is no validator
step on reads or on generated items; nothing feeds a teacher's correction back into reading.
`verify.py`, `mark()`, `rung_for()` and the `item_generate` prompt assume `a op b` arithmetic, so
a second subject cannot be added by rows today, though the data model (`skill.domain`, `tenant_id`
on every table, `item.spec` jsonb, `prompt` rows) already can.

Nimish's requirements, verbatim in intent: build it the right way now; it scales across subjects
and concurrent users within ~12 days; item creation is one master prompt per subject plus the
skill map; there are validation/confirmation layers on questions and on reads; the system gets
better at reading and understanding as it ingests more and as teachers correct it.

**Outcome:** dropping a scan in a folder produces candidates, a validator's verdict and a queue
count without anyone typing a command, and doing it twice changes nothing; a new subject is rows
plus at most one verifier module; every teacher correction becomes memory, gold and routing.

## Decisions taken (change any on review)

| # | Decision | Why |
|---|---|---|
| D1 | **n8n now, self-hosted in Docker, F3 first.** Supersedes `ARCHITECTURE.md` §8 "n8n arrives at N7". | The hand-run CLI is what produced the double import; the first two days *are* the read loop. ADR 0003 already rejected n8n Cloud (children's photos through a third party). |
| D2 | **n8n carries ids only** — capture ids, run ids, counts. Never a name, a path with a name, or an image. | n8n stores every node's payload in its execution log; rule 6 says scans never enter a log. A CI lint enforces it. |
| D3 | **Duplicates are voided, not deleted:** `capture.superseded_by`; the graph reads only live captures. | Rule 4, evidence is append-only. The rows stay; they stop counting. |
| D4 | **Validators are single-shot prompts** (`validate_read`, `validate_item`), each a `prompt` row with a JSON schema, gold and an eval. | Consistent with ADR 0006 (no harness). "A small agent that validates" = one fixed-shape call whose verdict code then acts on. |
| D5 | **Subject = a `subject` row + prompts keyed by subject + an optional verifier module.** Verifier is decisive on numbers where it exists (maths); the validator prompt + a ratified first sample is the guarantee where it does not. | Extends ADR 0005. Code can't verify a biology answer; a model plus a person can. |
| D6 | **The learning loop is rows + retrieval + eval gating, not model training.** Corrections → per-child reading notes and few-shot examples in the prompt, gold rows, and routing that adapts. | Frontier vision models cannot be fine-tuned by us; the memory and the prompt can learn. New ADR 0007. |
| D7 | **Haiku for every read and validate; Sonnet only by explicit row change.** A daily budget row; the adapter refuses past it. | Nimish: "use haiku or sonnet for majority/all tasks… use the key judiciously". |
| D8 | **Pilot on this Mac (Docker compose: engine + n8n); VPS in Mumbai before any teacher-facing run.** | SPEC §14.5. Recommend a ₹1,500–2,500/mo VPS; Nimish's spend decision, not blocking the pilot. |
| D9 | **Pilot notification = the Capture screen's queue count; no WhatsApp/email node yet.** | Channel is an open decision (SPEC §14.2). Adding a node later is one box. |
| D10 | **Drive trigger later; inbox folder now.** n8n's Local File Trigger on `~/cornerstone/assessments/inbox/`. | The Google OAuth click is Nimish's; the folder needs nothing and proves the flow. |
| D11 | **FastAPI handlers are plain `def` over the existing sync psycopg `db.connect()`**, with a `psycopg_pool`. | Rule 10 (extend, don't rewrite); FastAPI runs sync handlers in a threadpool. Deliberate exception to the async-handler house rule, recorded in ADR 0008. |

## Architecture after this plan

```
inbox/ or Drive ──n8n F3──> POST /ingest (idempotent: sha256+child+paper)
                            POST /read   (read prompt → validate_read prompt → confidence)
                            POST /mark   (lookup or rubric, by subject)
                            n8n writes nothing but ids; Capture screen shows "N to confirm"
Achal confirms/settles in the app ──> confirm_results / resolve_result (SQL, unchanged)
                                      + read_correction + gold rows (new)
n8n F3-nightly ──> POST /graph/rebuild → POST /profiles/rebuild → POST /bank/fill (top-up)
n8n F1 ──> POST /bank/fill {subject, skill_set, difficulty} (generate → verifier? → validate_item → sample|approved)
```

Engine layout additions (all inside `packages/engine/engine/`):
`api/app.py` `api/deps.py` `api/routes/{ingest,read,mark,commit,graph,bank,week,runs}.py`
`subjects/__init__.py` `subjects/maths.py` (moved: `assess/verify.py` rules, `assess/misconceptions.py` predictors, `legacy.rung_for/parse_expr/mark`)
`learning.py` (corrections → profile, gold, routing) · `render_pdf.py` (PyMuPDF, replaces the `pdftoppm` subprocess)

### Chunk 2 — the engine as a service (day 2) — done, with two deliberate departures from this text

Files, as built: `engine/api/{app,deps,idempotency,models}.py`, `engine/api/routes/{capture,
children,graph,bank,runs}.py`, `packages/engine/Dockerfile`, `deploy/compose.yml`,
`packages/engine/tests/api/*.py` (7 files, 41 tests). Deps: `fastapi`, `uvicorn[standard]`,
`psycopg-pool`, `httpx` (tests) — added to `pyproject.toml`, not `psycopg_pool` alone as first
written (the PyPI package is `psycopg-pool`; the import is `psycopg_pool`).

**Departure 1 — no `/read` split, no `/mark` split.** The original bullet said `/ingest` splits
`legacy.import_scan` into a cheap `ingest()` and an expensive `read()`. Nothing consumes that
split today — chunk 4 hasn't designed a workflow that needs two separate HTTP calls where one
already exists, tested, and (since chunk 1) already idempotent. Splitting a working function on
spec rather than on a real caller is exactly the premature abstraction CLAUDE.md's ladder rule 2
warns against. `/ingest` wraps `import_scan` whole; `/mark` wraps `legacy.remark` (re-mark
existing candidates, no model call) instead of a `/read`+`/mark` pair that doesn't exist yet. If
chunk 4 genuinely needs the split, it is a small, well-scoped addition then — not a guess now.

**Departure 2 — `/prescribe`, `/assemble`, `/render` deferred, not built.** These need a real
answer to "where does a rendered PDF live when the engine runs in a container" (a volume? object
storage? served back to n8n as bytes?) that chunk 2 has not earned yet — nothing in F3
read-and-respond (chunk 4) calls them. Building them now, without that design, is how a route
ships with a shallow test and a wrong assumption baked into its shape. Deferred to a chunk that
states the storage answer first.

**Also built, not originally listed:** `/children/find` (wraps `roster.find` — without it nothing
can turn a folder name into a `child_id` before calling `/ingest`); an `InProgress` → 409
exception handler in `app.py` (the first draft raised a bare `RuntimeError` for a genuine
concurrent duplicate — caught only by testing `run_idempotent` *and separately* testing the same
scenario through a real HTTP call, which is what surfaced that the exception was never translated
to a response at all); `flow_run.result jsonb` (migration `20260920090000_flow_run_result.sql`,
folded into chunk 2's date rather than chunk 1's since nothing needed it until now) — an idempotent
replay has to return *something*, and there was nowhere to put it.

- `X-Engine-Key` header checked in `require_engine_key`; refuses with 500 (not 401) when
  `ENGINE_KEY` itself is unset or empty — an unconfigured secret must never let an unset header
  match it. 401 for a present-but-wrong key.
- Every write route: `Idempotency-Key` header, or (no header) a key derived from the request body
  (`derive_key`, sha256 of the sorted-key JSON) → `run_idempotent`, which claims a `flow_run` row
  via `INSERT … ON CONFLICT … WHERE (idempotency_key IS NOT NULL) DO NOTHING`, runs the function
  at most once, and on a previous failure *reclaims* the row for a retry rather than leaving the
  key permanently stuck. A row still `running` (a genuine concurrent duplicate) raises
  `InProgress` → HTTP 409, never a second run.
- Routes over existing, already-tested functions: `/ingest` → `legacy.import_scan`; `/mark` →
  `legacy.remark`; `/commit` → `legacy.confirm`; `/graph/rebuild` → `graph.rebuild`; `/bank/fill`
  → `bank.fill`; `/children/find` → `roster.find` (no idempotency wrapper — a read, correctly
  logged twice if called twice); `/runs/{id}` and `/health` are pure reads.
- `deps.py`: `get_conn` yields `db.connect()` normally, or a `psycopg_pool.ConnectionPool`
  connection when `ENGINE_POOL=1` (set in the Docker image); one request is one transaction,
  committed on success and rolled back on any exception, via the same context-manager behaviour
  `db.connect()` already has.
- Dockerfile: multi-stage (`uv sync` in a builder stage, only the venv copied into the runtime
  stage), `libglib2.0-0`/`libgl1` installed for `opencv-python-headless`. `deploy/compose.yml`:
  engine + n8n, both reading the repo-root `.env`; n8n's execution data pruned at 7 days (a scan's
  path can carry a child's name — rule 6 — until chunk 4 designs the workflow properly).

Criteria:
1. `uv run pytest -q tests/api` → 41 passed: 401 without a key, 500 when `ENGINE_KEY` is unset, a
   409 (not a 500) for a call still `running`, a retried `/ingest`/`/mark`/`/commit`/`/bank/fill`
   call with the same key running its underlying function exactly once, `/bank/fill` specifically
   proven not to double-spend a model call on a retry, `/runs/{id}` returning a real row's tokens
   and cost. `uv run pytest -q` (the whole engine suite) → 182 collected, all green.
2. `docker compose -f deploy/compose.yml build engine` succeeds; `docker compose -f
   deploy/compose.yml up -d engine && curl -s localhost:8000/health` → `{"ok":true}`.
3. `curl -X POST localhost:8000/graph/rebuild -H "X-Engine-Key: $ENGINE_KEY" -d '{}'` →
   `{"states": N, "already": false}` and a `flow_run` row with `trigger = 'http'`, `flow =
   'graph_rebuild'`.

### Chunk 3 — validate the read, capture corrections, grow gold (days 3–4)

Files: `supabase/seed/prompts/validate_read.v1.txt` (+ schema in `prompts.json`),
`engine/learning.py`, `engine/api/routes/read.py`, `supabase/migrations/…_resolve_with_read.sql`
(`resolve_result` gains `p_read text`, writes `read_correction` + `gold`), `apps/web/app/(app)/growth/[id]/page.tsx`
+ `actions.ts` (the settle form gets a "child wrote" field and a misconception picker),
`engine/cli.py eval`.

- `validate_read` v1: input = the masked page + the transcription; output per answer
  `{n, part, agree, suggested, reason}` and `page_ok`. Haiku.
- Confidence and routing (code): `read_confidence = 1.0` when validator agrees, `0.5` when it
  suggests a different value, `0.0` when unreadable; route to the queue when confidence <
  `read.auto_confirm_above` **or** the (child, format) overturn rate over 30 days >
  `read.route_above_overturn`. Everything else stays a candidate for one-tap confirm.
- Every settle with an edited read → `read_correction` + `gold(truth)`; every plain confirm of a
  validator-agreed read → `gold` too (agreement is also truth).
- `engine eval legacy_extract|read_cells [--version N]`: run the prompt over every gold capture,
  print agreement per field; `--activate` flips `active` only if agreement ≥ the active version's.

Criteria:
1. Tests: validator disagreement routes to the queue; agreement does not; a settle with an edit
   writes `read_correction` and `gold`; eval refuses to activate a worse version.
2. `uv run engine eval legacy_extract` prints `agreement N/M` over ≥ 20 gold rows after Achal's
   first sitting.
3. On the child page, settling an answer with a typed correction shows the corrected value in the
   step's table on reload.

### Chunk 5 — subject plugins, validate_item, sample ratification (days 6–8)

Files: `engine/subjects/__init__.py`, `engine/subjects/maths.py` (moved from `assess/verify.py`
rule checks, `assess/misconceptions.py` predictors, `legacy.rung_for/parse_expr/mark`),

- `subjects.verifier(code)` returns the module named in the `subject` row or `None`.
  `bank.fill`: generate with the subject's `item_generate` row (subject-specific master prompt,
  else generic) → verifier `problems()` if present → `validate_item` verdict → status `sample`
  until the skill set is `live`, then `approved`. Failures counted in `flow_run` by reason.
- `validate_item` v1: input = item + spec + philosophy; output `{ok, problems[]}` on: answerable,
  one correct answer, matches objective and the difficulty words, language for the grade, no
  forbidden words, distractors plausible. Haiku.
- The maths master prompt keeps `op/a/b/answer`; the generic one asks for `{question, answer,
  rationale, options?, rubric?}`; `item.spec` stores either; `mark_mode` from the `subject` row:
  `lookup` (numbers/options) or `rubric` (→ `needs_teacher`, rubric shown in the queue).
- Legacy import rung: from the paper definition (already confirmed by the person entering it);
  the maths plugin only *suggests*.

Criteria:
1. Existing tests green with `verify`/`misconceptions` imported through `subjects.maths`.
2. Proof by rows: insert a `subject` row `SCI`, three skills, two rungs, one skill set, an
   `item_generate` row with `subject = 'SCI'`, then
   `uv run engine bank fill --set SCI.LIFE.1 --difficulty Medium --n 5` → 5 items with
   `status = 'sample'`, each carrying a `validate_item` verdict; `git diff --stat` shows Python
   changes only under `engine/subjects/` and `render.py` (recorded in STATE.md).
3. Ratifying the sample on the skill-set screen flips `status` to `live`; the next fill lands `approved`.
4. `uv run engine eval item_generate --subject NUM` pass rate ≥ today's.
