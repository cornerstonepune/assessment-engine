Student Operating System
Complete End-to-End Architecture, Workflow Specification & Jev Integration Blueprint
Scope: A build-ready conceptual and technical architecture for a school-wide operating system that
manages the student lifecycle from curriculum design through teaching, assessment, evaluation,
observation, intervention, progression, reporting and institutional learning.
Core thesis: the school becomes a continuously learning system. The persistent object is the student
state; the school knowledge graph defines what should be learned; workflows determine what should
happen; AI generates and interprets; Jev supplies bounded decisions; deterministic software enforces
policy; teachers retain approval authority.

1. Executive Architecture Decision
Build this as a Student Operating System, not an LMS. An LMS primarily stores content and assignments. This
system maintains a longitudinal, evidence-backed model of each child and continuously uses it to determine what
should happen next.
The OS should have six foundational layers: (1) School Knowledge Graph, (2) Content & Pedagogy Layer, (3) Student
State Graph, (4) Decision Fabric including Jev, (5) Workflow/Orchestration Layer, and (6) Human Interfaces &
Governance.
Jev's role: a bounded decision substrate. It should classify, score, choose, verify and route. It should not
be the source of truth, the database, the workflow engine, or the primary content generator.
Current TypeSafe documentation describes Jev/System One as an API for structured Choice, Score and Noul (yes/no)
decisions. TypeSafe's current API documentation shows a shared state plus up to 32 named questions per request.
IciteIturn0search6I
The architecture below deliberately keeps Jev behind a provider-neutral Decision Service. That means the OS can use
Jev heavily without making Jev an architectural single point of failure.

3. What Is the Brain? What Is the Nervous System?
The brain is not a model. The brain is the combination of the School Knowledge Graph + Student State
Graph + Policy/Workflow Engine.
School Knowledge Graph = institutional memory. It defines what the school believes should be learned and how
concepts relate.
Student State Graph = current memory of the child. It records evidence, mastery estimates, misconceptions,
observations, interventions and trajectories.
Decision Fabric = interpretation. Jev and other models turn evidence into bounded judgments.
Orchestrator = executive function. It converts decisions into workflow transitions and tasks.
Teacher = constitutional authority. Humans approve consequential curriculum, assessment and developmental
decisions.
Event Store = memory of what actually happened. It allows the system to replay, audit and learn from every action.
So when we say Jev can become the 'nervous system', we mean it can sit at thousands of small decision points
between state and action. It senses/assesses, produces structured signals, and triggers the appropriate workflow. It
does not become the school itself.

8. W01–W03: Curriculum & Pedagogy Workflows
W01 — Curriculum design
Input: standards + grade + subject + master skill map. Output: versioned learning outcomes, levels, prerequisites and
curriculum sequence. Human: curriculum team.
W02 — Pedagogy generation
Input: skill + outcome + level + pedagogy philosophy + constraints. LLM generates activity, materials, teacher moves,
observation points, student outcomes, theory alignment, differentiation and assessment opportunity.
Jev checks: alignment, age appropriateness, prerequisite sufficiency, target-skill coverage, misconception coverage,
assessability and implementation risk.
W03 — Curriculum QA
AI-generated content is independently evaluated before human approval. Store both generated version and approved
version. Curriculum team edits/approves; approval locks a version.

9. W04–W09: Assessment → Evaluation → Mastery
W04 Question bank: every question is mapped to skill, level, misconception, evidence type, rubric and prerequisite.
W05 Assessment assembly: deterministic filters narrow the pool; Jev selects/weights diagnostically useful items; code
enforces coverage, length, difficulty and exposure constraints.
W06 Approval: teacher sees assessment, rationale and relevant student state, then approves/edits/rejects.
W07 Submission: scan/image → page detection → question segmentation → handwriting/OCR/multimodal extraction.
W08 Evaluation: deterministic scoring where possible; symbolic math where possible; multimodal model for working;
Jev for bounded error classification, evidence sufficiency and escalation.
W09 Mastery: combine objective evidence with statistical/probabilistic update. Jev can provide interpretation signals,
but the canonical mastery state should be maintained by your own state engine.

10. W12 Observation Engine
Teacher can submit structured form or voice note. Speech-to-text creates transcript. Extraction layer identifies student
references, academic observations, behaviour observations, engagement, social interactions, curriculum/pedagogy
feedback and operational issues.
Jev then evaluates bounded questions such as: Was a specific skill mentioned? Was a misconception mentioned? Is
there evidence of transfer difficulty? Is this likely a recurring pattern? Should this enter persistent state? Does this need
teacher/coordinator review?
Observation objects should preserve raw transcript/audio reference, extracted claims, evidence spans, confidence,
author and timestamp. Never discard the source evidence behind a qualitative inference.

11. W10–W11 Intervention Loop
Detect: Student State indicates gap.
Diagnose: Jev classifies likely issue and evidence sufficiency.
Select: Jev chooses among validated interventions.
Approve: teacher confirms.
Execute: activity/lesson occurs.
Observe: teacher records qualitative response.
Reassess: targeted assessment.
Update: mastery and intervention-effectiveness evidence stored.
Next: continue / intensify / change intervention / progress.
This loop should become the core adaptive mechanism of the school.

13. Agentic Platform: What Should We Use?
Recommendation: use a durable workflow/state-machine architecture as the core; use agent
frameworks only inside bounded workflows. Do not make a free-form multi-agent swarm the backbone of
a school system.
LangGraph: a strong candidate for workflows requiring explicit state, branching, persistence and human interruption. Its
current human-in-the-loop documentation describes interrupting execution, persisting graph state, and resuming after
approve/edit/reject/respond decisions. IciteIturn0search8I
OpenAI Agents SDK: also viable for code-first agent workflows. Current documentation supports tools, handoffs,
guardrails, human review, resumable state and tracing. IciteIturn0search2Iturn0search7I
My recommendation: if your team is building a Python/TypeScript product and wants maximum explicit control, use
LangGraph for long-running, stateful workflows or the OpenAI Agents SDK where agent loops/handoffs are
genuinely useful. Do not use both as co-equal orchestration layers in v1. Pick one workflow runtime.
Jev should sit below either framework as a Decision Service. The workflow engine owns state transitions; Jev owns
bounded judgments.

18. Model / Workflow Improvement Flywheel
Production event → decision made → teacher accepts/edits/rejects → outcome observed →
disagreement captured → example enters evaluation set → decision spec/prompt/model tested → offline
evaluation → shadow deployment → online A/B or controlled rollout → new version → monitor → repeat
Do not let production automatically retrain or rewrite prompts. The improvement pipeline should be controlled, versioned
and reversible.

19. Knowledge Graph + Student Graph + Decision Graph
Use three related but distinct graphs:
• School Knowledge Graph: what should be learned and how concepts relate.
• Student State Graph: what this child has demonstrated and what evidence supports it.
• Decision/Evidence Graph: why the system made a decision, what evidence it used, what human did, and what
happened afterward.
This gives you explainability and longitudinal learning. A report statement can trace back to evidence; an intervention
can trace to a diagnosis; a diagnosis can trace to assessment work; curriculum feedback can trace to aggregated
student outcomes.

20. Reporting + Handover
Reports should be generated from state, not invented from scratch.
Pipeline: Student State → evidence selection → period comparison → growth analysis → narrative generation → Jev
evidence verification → teacher approval → final report.
For handover, use the same mechanism: summarize only high-value evidence relevant to the next teacher's context.
Include confidence, recency and what has already been tried.

22. Governance, Safety & Privacy
• Role-based access: teacher, coordinator, curriculum team, principal, parent, student, admin.
• Every sensitive action is auditable.
• Separate raw evidence from derived inference.
• Retention policies for audio, scans and student records.
• No permanent behavioural labels from single observations.
• Human approval for consequential academic/developmental decisions.
• Model/provider version recorded for every AI-derived decision.
• Ability to delete/correct derived records while preserving legally required audit history.
• Data minimization: only provide each model the state required for its decision.
• Vendor contracts and data-processing terms must be reviewed before production.
OpenAI's current agent tooling illustrates the general pattern of tracing, guardrails and human approvals; the school
should implement equivalent controls regardless of model vendor. IciteIturn0search1Iturn0search7I

23. Observability & Debugging
Every workflow execution should have a trace ID. A trace should show: trigger → state snapshot → model calls → Jev
decisions → tool calls → human approvals → state mutation → resulting event.
OpenAI's current Agents SDK tracing records model generations, tool calls, handoffs, guardrails and custom events;
this is the level of observability your own platform should aim for irrespective of whether you use that SDK.
IciteIturn0search1Iturn0search3I
Build a replay facility: take a historical event and rerun a decision against a new model/spec without
changing production state. This is essential for safe improvement.

28. Final Architecture Thesis
The Student OS should become the operating system of the school, not another application used
by the school.
The distinction is profound. In a normal school, curriculum, teacher planning, assessment, observations, interventions,
reports and handovers are separate human processes connected by spreadsheets, meetings and memory. In this OS
they become states and workflows connected by evidence.
The school gradually becomes a closed-loop learning organization: it knows what it intends to teach; knows what was
actually taught; knows what each child demonstrated; detects where the child is struggling; selects an intervention;
measures whether it worked; learns which pedagogies work; improves curriculum; and carries the resulting knowledge
forward to the next teacher and next cohort.
Jev is valuable because the system contains an enormous number of small decisions. It can make those
decisions cheap, fast and structured. But the actual institutional intelligence comes from the combination
of Knowledge Graph + Student State + Evidence + Decision Fabric + Workflow Engine + Human
Governance.
Therefore: make the Student State and event architecture permanent; make the workflow contracts explicit; make
every AI decision a versioned Decision ID; integrate Jev behind a provider-neutral Decision Service from Day Zero; and
let autonomy grow only as evidence justifies it.
That is how this stops being 'an AI school platform' and becomes the core operating system through
which the school actually runs.
